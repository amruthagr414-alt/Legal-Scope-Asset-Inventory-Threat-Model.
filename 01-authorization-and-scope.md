# 1. Authorization and Scope

## 1.1 Objective

Define a controlled and legally bounded environment for learning security assessment practices. The engagement identifies the assets to be considered, the boundaries within which work may occur, and the conditions under which all activity must stop.

## 1.2 Authorization basis

This document is a **student lab plan**, not a claim of authorization from an external organization. The student may assess only systems they own or systems for which the responsible owner has provided explicit written permission.

For this project, the intended target is an intentionally vulnerable training application hosted locally on the student's own computer. If the lab is not owned or controlled by the student, written permission from its owner is required before testing.

## 1.3 In-scope components

| ID | Component | Boundary |
|---|---|---|
| S-01 | OWASP Juice Shop instance | Local instance only |
| S-02 | Browser used to access the lab | Student-owned device |
| S-03 | Local application data store | Only the lab's own data |
| S-04 | Local application logs | Logs generated by the lab |
| S-05 | Lab configuration | Local configuration files |

## 1.4 Out-of-scope components

- Public websites, public IP addresses, and external servers
- University systems, networks, portals, or accounts
- Other students' or family members' devices
- Third-party databases, cloud services, and production environments
- Any system for which explicit authorization has not been obtained
- Denial-of-service, destructive, persistence, or data-exfiltration activity

## 1.5 Engagement assumptions

- The application is used only as a training target.
- Test accounts contain synthetic data only.
- The lab is not exposed to the public internet.
- Testing is non-destructive and limited to approved learning objectives.
- Any change to scope requires approval from the system owner before work continues.
